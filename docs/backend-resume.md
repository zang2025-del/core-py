# permgate：后端开发简历写法与面试应答

> 目标岗位：后端开发（Python 服务端）
> 定位：这是一个**服务端系统**，不是「我把一个 agent 项目改成了后端」

---

## 0. 先说清楚定位

同一个项目，三种写法，面试官的反应完全不同：

| 写法 | 面试官的反应 |
|---|---|
| ❌「我用 FastAPI 写了个权限服务」 | 又一个 CRUD 项目。追问：难点在哪？ |
| ❌「我把一个 agent 项目的安全策略翻译成了后端」 | 那后端部分不是你做的。追问：架构是你设计的吗？ |
| ✅「一个 agent 权限决策服务。**我先把判定层做成纯函数，然后才有资格谈性能和一致性**」 | 追问：为什么？怎么测的？ |

**核心叙事只有一句**：

> 这个服务的领域层是纯的——没有 IO、没有配置、没有日志。这不是洁癖，
> 因为它买到三件事：规则层能离线评测、能穷举测试，**而且性能瓶颈的位置变得显然**。
> 我最后测出来瓶颈在审计写入而不是规则匹配，与直觉相反——**这个结论只有在
> 纯函数边界存在的前提下才能被查证，而不是被争论。**

这句话把「代码写得干净」从审美问题变成了工程问题。后端面试官要听的是后者。

## 1. 简历文案

### 1.1 完整版（项目栏）

```
Agent 工具调用权限网关（permgate） | 独立完成 | 2026.10
FastAPI · SQLAlchemy 2.0 · SQLite/PostgreSQL · Prometheus · Docker · 766 测试 / 覆盖率 94%

S 背景：AI agent 会执行 shell 命令，而"这条命令危不危险"无法用规则穷举——
        terraform destroy 与 kubectl delete namespace production 是灾难性的，
        任何"看起来危险"的正则都抓不到。需要一个独立的决策服务，
        把裁决从 agent 进程里拆出来，并让每次裁决可解释、可审计。
T 任务：设计并实现一个可部署的权限决策服务：分层架构、事务边界、
        缓存一致性、可观测性、可压测的性能，并把上一轮研究的安全指标
        变成可回归的质量门禁。
A 行动：
  · 四层架构（api → services → storage → domain），**domain 层做成纯函数**：
    无 IO / 无配置 / 无日志，decide() 是它参数的函数。换来三件事：
    规则层可离线评测、可穷举测试、性能瓶颈位置可单独计时
  · 两阶段决策 API：POST /v1/decisions 返回裁决 + decision_id，
    POST /v1/decisions/{id}/answer 记录人的回答。决策落库为带 id 的资源
    而非无状态调用——因为弹框是一个往返，服务必须在中间记住"问题"
  · 授权存储：SQLite + SQLAlchemy 2.0，scope 用空串而非 NULL
    （三家的 UNIQUE 都把 NULL 当互不相同，可空 scope 会让最常见的
    tool 级授权重复插入）；幂等写入靠唯一约束 + 冲突重读；
    决策与它创建的授权在同一事务；审计表 append-only（**数据库触发器强制**）
  · 授权缓存的一致性设计：**失效在 commit 之后**而非之前——
    先失效会留一个窗口，并发请求把写之前的集合缓存下来带上新 TTL，
    写就永远不可见。撤销立即生效，TTL 只作为跨进程兜底
  · 可观测性：Prometheus 指标（决策计数按 verdict/rule/tool 标签、
    自定义分桶的延迟直方图、缓存 hit/miss/eviction/invalidation）、
    结构化日志 + 请求 ID 贯穿、liveness/readiness 分离
  · **分层延迟压测**，把同一批语料在引擎/服务/HTTP 三层分别计时
R 结果：
  · **规则层只占一次请求的 3%**（p50 27µs vs 服务 p50 813µs）——
    优化匹配器等于什么都没做
  · **瓶颈是审计写入，不是授权查询**：关掉审计 p50 813→499µs、
    p99 3175→993µs；而授权缓存只省 18%。**结论与直觉相反**
  · **并发吃掉的是尾延迟不是中位数**：8 线程 p50 几乎不动（813→884µs），
    p99 从 3.2ms 涨到 110ms——SQLite 串行化写入。据此把下一轮靶子定为
    审计批量提交，并写明为什么这一版故意不做
  · 完整服务 p50 813µs / p99 3.2ms / 1019 ops/s；纯引擎 28,958 ops/s
  · 766 个测试 12 秒跑完、覆盖率 94%、`mypy --strict` 与 `ruff` 全绿；
    其中 **119 条命令 × 4 项输出与原实现逐字对拍**，
    证明这是一次被验证过的移植而不是重写
  · 把已发布的安全指标钉成回归门禁：白名单召回 100% / 误伤 0%，
    无人值守敞口 8→0 且合法命令 24/24 全放行
```

### 1.2 精简版（3 行）

```
Agent 工具调用权限网关 | FastAPI · SQLAlchemy · Prometheus · Docker
· 四层架构并把 domain 层做成纯函数，换来规则层可离线评测、可穷举测试、
  以及性能瓶颈位置可单独计时——据此测出规则层只占请求的 3%、
  真正瓶颈是审计写入（关掉它 p50 减半、p99 降到 1/3），与直觉相反
· 授权缓存的一致性：失效放在 commit 之后，撤销立即生效，TTL 只作跨进程兜底；
  幂等写入靠唯一约束 + 冲突重读；审计表 append-only（数据库触发器强制，非代码约定）、与授权同事务
· 766 测试 / 覆盖率 94% / mypy strict 全绿；119 条命令与原实现逐字对拍；
  安全指标钉成回归门禁，CI 七个 job 强制
```

### 1.3 三条原则

1. **每条 bullet 带数字。** 「优化了性能」不加分，「规则层只占 3%、关掉审计 p50 减半」加分。
2. **写反直觉的结论。** 「我猜是数据库读，测出来是写」比「我做了性能优化」可信得多——
   因为它证明你真的测了。
3. **写边界。** 没有沙箱、多进程撤销有 TTL 上界、不做语义判断——主动说出来。

## 2. 90 秒口述版

> 我做的是一个 **agent 权限决策服务**。背景是：AI agent 会跑 shell 命令，
> 而"这条命令危不危险"没法用规则穷举——`terraform destroy` 和
> `kubectl delete namespace production` 是灾难性的，但任何"看起来危险"的正则
> 都抓不到，因为危险在程序做什么，不在它怎么写。
>
> **我做的第一个决定是架构上的，而且它决定了后面所有事：我把领域层做成纯函数。**
> 分类器和决策引擎里没有 IO、没有配置、没有日志，`decide()` 就是它参数的函数。
>
> 这不是洁癖。它买到三件事：**第一**，规则层能离线评测——我拿 49 条标注命令
> 加 11 条真实事故命令跑完整分类器，不需要服务器和数据库；**第二**，能穷举测试，
> 766 个测试 12 秒跑完；**第三**——这条最关键——**性能瓶颈的位置变得显然**。
> 因为 `decide()` 是纯的，它唯一可能慢的原因就是它的输入拼装得慢，那我把性能
> 预算压到授权查询和审计写入上就行了。
>
> **然后我分层测了一遍，结论和我预期相反。** 纯引擎 p50 是 27 微秒，
> 完整服务是 813 微秒——**规则层只占 3%**，优化匹配器等于什么都没做。
> 我本来以为瓶颈是数据库读，因为每次决策都要查一遍授权。结果关掉审计写入，
> p50 直接减半、p99 降到三分之一；而加上授权缓存只省 18%。**瓶颈是写，不是读。**
>
> 还有一条：8 线程并发下 p50 几乎没变，p99 从 3.2 毫秒涨到 110 毫秒。
> SQLite 串行化写入，请求在排队——**中位请求没事，排在七个写者后面那个有事**。
>
> **所以我下一轮的靶子是审计写入的批量提交，而这一版我故意没做。** 因为让那次
> 写入变便宜的每一种办法——缓冲、异步、批量——都在拿审计表存在的意义去换：
> 崩溃时丢一批审计行，是审计表唯一不能接受的事。我把测量和取舍写进了文档，
> 而不是悄悄做掉。
>
> 另外还有一块我做得很满意：授权缓存的一致性。**撤销必须立即生效，不能等 TTL。**
> 关键是失效要放在 commit **之后**——如果先失效，会有一个窗口，并发请求把写之前
> 的授权集合读出来、缓存下来、还带上新的 TTL，那次写就永远不可见了。这是个
> 很窄的竞态，但它的后果是"用户撤销了一个授权，服务还在照着它放行"。

**最后 40 秒是这段的价值。** 大多数候选人到这里会说"我把性能优化了 30%"。
你说的是"我测了，结论和我猜的相反，我知道下一步该做什么，也知道为什么现在不做"。

## 3. 杀手题

### 3.1 「这不就是 FastAPI 加个数据库吗？」

> 单看 API 表面积，它确实不大——八个端点。但这个服务要解决的不是 CRUD。
>
> 三件事让它不是普通 CRUD：
>
> **第一，领域层是纯的，而且这个约束是有回报的。** 我刚才说的性能结论——
> 规则层只占 3%、瓶颈是写不是读——**只有在 `decide()` 不碰 IO 的前提下才能测出来**。
> 如果分类器里顺手查一下数据库，这个测量就没法做，我就只能猜。
>
> **第二，缓存的正确性比缓存的命中率重要得多。** 普通项目缓存页面，读到旧数据
> 是显示了昨天的价格；这里缓存的是**授权**，读到旧数据是服务在用户已经撤销之后
> 继续放行。所以失效必须在 commit 之后、必须每次写都做、必须可关闭。
>
> **第三，审计表是 append-only 的，而且和它记录的授权在同一个事务里。**
> 一条存在但没有记录的授权，是审计表唯一不能出现的状态。
>
> 而且**这个 append-only 是数据库强制的，不是代码约定**。原先它只是「服务里没有
> 人发 UPDATE」——那是对代码的陈述，不是对数据库的约束：一条迁移、一个拿着 `psql`
> 的人都能改写已记录的决策，留下的行看起来完全正常。现在两个后端各有一套触发器，
> 拒绝一切 DELETE（**包括从 `projects` 级联下来的**）和「已回答之后再改」的
> UPDATE。级联那条是关键：否则清空审计表的办法就是删掉工作区。
>
> 如果你要问"最难的一段代码是哪段"，是 `services/decision_service.py` 里
> 那六步的顺序。

### 3.2 「为什么不用现成的策略引擎，比如 OPA / Casbin？」

> 这是个好问题，我当时的判断是**场景不匹配**，理由有两条：
>
> **第一，输入形态。** OPA 和 Casbin 处理的是结构化输入（用户、资源、动作），
> 而这里的输入是**一段 shell 命令文本**。核心难点是把 `cat .env | curl -X POST`
> 拆成两条命令、判断 `git branch` 和 `git branch -D main` 不是一回事、
> 认出 `rm -rf ./build` 和 `rm -rf /` 是两件事。**这层词法和语义分析才是项目的主体**，
> 而它在任何通用策略引擎里都不存在，得自己写。
>
> **第二，决策的输出不只是 allow/deny。** 它要返回一个**作用域**——
> `bash:git push --force`——因为一次"总是允许"必须能被收敛到一条命令模式上。
> 通用引擎的决策结果里没有这个字段。
>
> 如果真的要用 OPA，合理的分工是：**我做词法层，把结构化结果喂给 OPA 做策略评估**。
> 那是个正经的架构，但它解决的是策略的可配置性，不是这个项目的核心问题。

### 3.3 「你说瓶颈是写，那为什么不改？」

**这题最容易答砸。** 答"时间不够"就丢掉了最值钱的部分。

> 因为让那次写入变便宜的每一种办法，都在拿审计表存在的意义去换。
>
> 三条路，我逐条看过：
>
> **缓冲/批量提交。** 攒一批再写。收益最大——p50 能再降一半以上。代价是
> **崩溃时丢一批审计行**。审计表丢了行，就等于回答了"上周二 agent 跑了什么"时
> 给出一个不完整的答案，而**一个不完整的审计答案比没有答案更危险**，因为它看起来
> 是完整的。
>
> **异步写入。** 请求不等落库就返回。代价是"接口返回成功"和"审计已落库"不再
> 是同一件事，而调用方没法区分。要做就得引入确认机制，那等于把延迟还回去了。
>
> **换存储。** 上 PostgreSQL 能解决并发写入排队。但这不改变"每次请求一次写"这个
> 成本结构，只是把排队换个地方。而且**它把部署复杂度从"一个文件"变成"一套服务"**，
> 对这个体量不划算。
>
> 所以我把它写成了文档里的下一轮靶子，并把取舍条件写清楚了：**要做到批量提交，
> 得先回答"崩溃时丢一批审计行，可接受的上界是多少"**。那是个产品决策，
> 不是技术决策，我不替它做主。

### 3.4 「你怎么知道移植是对的？」

> 我没有"相信"它是对的，我做了对拍。
>
> 领域层的规则是从我上一轮项目里移植过来的，那个实现有四轮实测加固。
> 移植的时候我写了个脚本，把原实现对 **119 条命令的四项输出**——
> 黑名单原因、白名单原因、执行层闸门、命令作用域——全部冻结成一个 TSV 夹具，
> 然后 `tests/unit/test_conformance.py` 每次运行都逐条比对，**包括"没有匹配"这件事**。
>
> 477 条断言。这是一次被验证过的移植，不是"我移植了"。
>
> **而且对拍过程中我发现了原报告的一处错误。** 原报告里「改造前的无人值守」
> 那一行，用的是**改造后**的执行层闸门，而不是当时真实存在的旧闸门。后果是把
> 16/24 报成了 24/24——等于替旧代码记了一次它没做过的放行。
>
> 敞口那一列（8/25）不受影响，因为两种闸门对危险命令判断一致，所以核心结论
> 仍然成立。但这正是"基线必须跑在原始代码上"那条纪律的又一次应验，而且这次
> 是在我自己的材料里。**新项目里我把闸门绑定在策略对象上，这个错误在结构上
> 不可能再犯。**

## 4. 后端考点速查

面试官会挑着问，每条都有确定答案。

| 考点 | 这个项目里的答案 |
|---|---|
| **事务边界** | 一次请求 = 一次事务。决策的审计行和它创建的授权同一事务提交——一次崩溃不能留下没有记录的授权。`session_scope()` 上下文管理器统一出口 |
| **幂等** | 授权写入靠 `UNIQUE(project_id, tool, scope)` + 冲突后重读，重放返回同一行而不是报错或重复。回答接口二次调用返回 **409**，因为重写一个人的决定是审计表绝不能允许的 |
| **并发** | 回答的原子性靠条件 UPDATE（`WHERE answer IS NULL` + `rowcount` 判胜负），不靠行锁——行锁在 SQLite 上被编译掉，只在 PG 生效，是个只存在于 CI 的保证。并发回答在两种后端上都测过。SQLAlchemy 连接池；SQLite 开 WAL + busy_timeout（把 "database is locked" 从异常变成等待）；`check_same_thread=False` 只在"一个连接同一时刻只属于一个线程"的前提下成立 |
| **缓存一致性** | 失效在 **commit 之后**；每次写都失效（包括没匹配到的撤销——调用方以为有东西在）；TTL 只作跨进程兜底；缓存可关闭。**多进程下的可见性延迟上界 = TTL，这是明示的缺口** |
| **索引** | `projects.root` 唯一索引；`grants(project_id, tool, scope)` 唯一约束 + `(project_id, tool)` 查询索引；`decisions(project_id, occurred_at)` 和 `(verdict, occurred_at)` 支持审计查询 |
| **为什么 scope 用空串不用 NULL** | SQLite / PostgreSQL / MySQL **都把 UNIQUE 索引里的 NULL 当作互不相同**，可空 scope 会让最常见的 tool 级授权重复插入，唯一约束形同虚设 |
| **错误契约** | 全部失败一个形状 `{"error": {code, message, details, request_id}}`；服务异常自带 `status_code`，映射写在异常类旁边；**未预期异常不泄漏文本**，只给 request_id，全文进日志 |
| **可观测性** | 指标标签是**封闭枚举**（rule 来自 `Rule` 枚举），防止基数爆炸——自由字符串当标签是打垮指标后端的经典方式；延迟直方图自定义分桶（默认桶从 5ms 起，会把所有流量放进第一个桶）；健康检查分 liveness / readiness，**liveness 不碰数据库**（数据库慢就重启进程，既不修数据库又丢在途请求） |
| **配置** | pydantic-settings，全部来自环境变量；**测试一律 `_env_file=None`**——曾经因为读到了环境里残留的 `PERMGATE_PREAPPROVED_SCOPES`，四个拒绝类测试静默变成了通过 |
| **迁移** | Alembic，URL 从应用自己的 settings 读（两处真相 = 迁移打到错的库上）。有一个用 `compare_metadata` 的测试断言**模型与迁移零差异**——这是「改了 models 忘了生成迁移，本地全绿、部署失败」那类 bug 的专用检查 |
| **自己文档里的流程也要跑** | README 的 curl 示例是**照抄真实响应**的，不是手写的。为了做到这点我把文档里的每一步跑了一遍——抓到三个测试套件没抓到的问题：示例里的 `scope` 少写了标志、首次请求 12ms 被当成判定成本、以及**两个端点对「项目标识」给出了不同的答案**（决策端点返回解析后的根，授权端点回显原始输入）。它们全都不是因为功能坏了，而是因为**没人问过「客户端怎么把这两个接口串起来用」** |
| **CI** | 七个 job：lint / types（mypy strict）/ test（3.10–3.12 矩阵，`--cov-fail-under=90`）/ postgres（同一套测试跑在 postgres:16 上）/ migrations（从空库迁移 + downgrade 往返）/ evaluation（重测安全指标）/ docker（构建镜像并打一次真实决策）。**每个门禁都是这个项目已经失败过一次的那一类** |
| **安全** | BYPASS 模式默认不服务，且在**边缘**拒绝而不是引擎深处；客户端默认不能自选运行模式（能选模式的客户端能选 BYPASS，整个服务就变成装饰） |
| **压测** | 最近邻分位（不插值），报的每个数字都是真实发生过的延迟；warm-up 与测量分离；**机器事实随数字打印** |

## 5. 诚实红线

| 不要写 | 为什么 |
|---|---|
| 「自研 agent 权限框架」 | 规则层移植自你上一轮项目，文档里写清楚了。含糊其辞比使用前作扣分更多 |
| 「高并发、支撑 XX QPS」 | 你没做过线上。实测是单机 1019 ops/s，写这个数字 |
| 「性能优化 30%」 | 你**没有**优化。你测出了瓶颈在哪并说明为什么这一版不改——这个更值钱 |
| 只报 p50 不报 p99 | 这个项目的 p99 是 p50 的 4 倍、并发下是 125 倍，省略它就是只报对自己有利的一半 |
| 「上了 Redis 缓存」 | 没有。缓存是进程内的，多进程一致性是明示的缺口 |
| 「有沙箱隔离」 | **没有。** 白名单不隔离进程，`make` 照样能跑任意 recipe |
| 「支持 PostgreSQL」 | 现在这句话有证据了：CI 的 `postgres` job 把整套测试跑在 postgres:16 上。但**没有生产负载验证**——并发写入的排队只在 SQLite 上量过，别把"测试跑过"说成"压测过" |
| 「并发安全」 | 回答路径的原子性有证据（条件 UPDATE，两种后端都测，且测试在旧实现上会失败）。但**只有这一条路径**被这么证明过——授权写入靠唯一约束，其余写入路径的并发行为没有同等强度的测试 |
| 把 33% 叫「误伤率」 | 那是打扰率，全部问在会不可逆丢东西的命令上，问得对。误伤率是 0% |

**正确姿态**：主动、清楚地说明哪些是移植的、哪些是新写的、哪些没做。
面试官不会因为你复用了自己的前作扣分，只会因为你**含糊其辞**扣分。
