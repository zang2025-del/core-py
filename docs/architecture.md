# 架构与工程决策

这份文档记录**每一个非显然的决定，以及它的代价**。没有代价的决定不在这里，
因为它们不需要解释。

---

## 1. 分层，和「领域层是纯的」这条约束

```
api/          HTTP、DTO、错误映射、依赖注入        ─┐
services/     事务边界、缓存失效、审计写入          │  可以有 IO
storage/      SQLAlchemy 模型、仓储、授权缓存       │
domain/       词法、规则表、分类器、策略、决策引擎  ─┘  **纯函数，零 IO**
```

依赖单向向下。`domain/` 不 import 任何其他层，也不 import SQLAlchemy、
FastAPI、structlog 或 `os`。

这条约束买到三件事，而且第三件是意外收获：

### 1.1 规则层能离线评测

`eval/` 用 49 条标注命令 + 11 条真实事故命令跑完整分类器和**四份冻结的历史
配置**，不需要服务器、数据库、网络。README 里所有安全数字来自这里。

如果 `decide()` 需要查一次数据库才能返回，这个评测就没法做——因为「改造前」
的配置需要的历史数据早就不在库里了。

### 1.2 规则层能被穷举测试

796 个测试 12 秒跑完，覆盖率 94%。规则矩阵、六个决策分支、`grant_for_answer` 的不对称——
每个分支一个测试，而不是被一个大的场景测试顺便覆盖。

### 1.3 性能瓶颈的位置变得显然

这是最重要的一条。因为 `decide()` 是纯的，**它唯一可能慢的原因就是它的输入
拼装得慢**。这把整个性能预算压到两个地方：授权查询和审计写入。

于是压测只需要分层做一次，就能得到确定答案：

| 层 | p50 | p99 | ops/s |
|---|---:|---:|---:|
| engine（零 IO） | 33µs | 142µs | 22,101 |
| service-uncached | 1,658µs | 5,312µs | 482 |
| service-cached | 1,407µs | 5,998µs | 529 |
| service-no-audit | **765µs** | **3,419µs** | 1,022 |
| service-8-threads | 1,829µs | 94,085µs | 575 |
| http-4-threads | 25,077µs | 64,368µs | 147 |

**这组数字比上一版慢，原因写在明处**：上一版 `results.json` 的 `executable`
字段是 `D:\Projects\Core-c++\.venv\Scripts\python.exe`——数字来自另一个
checkout，本仓库从未复现过。而这一版每个业务请求都多了鉴权：每请求 SQL 从
2 条变 4 条（多一次 token 查询、一次 roots 查询）。HTTP 层差距最大，因为它
同时吃到鉴权和栈开销。

换后端的对照见 §6.1 之外的另一份测量：`loadtest/backends.py`，结论是
**没有一个后端占优**——SQLite 守住中位数、丢掉尾部，PostgreSQL 反过来，
到 16 线程两者收敛到同样差的尾部。

**代价**：服务的每一层都要负责把 `decide()` 的输入拼装好（`GrantSet`、
`PolicyProfile`、`PolicyRegistry`）。这个拼装逻辑在 `services/decision_service.py`
里，是唯一需要小心的地方。

## 2. 决策顺序

见 `domain/engine.py` 的 `decide()`。六个分支，**顺序就是安全模型**：

```
1. BYPASS 短路一切
2. 只读工具永不打扰人
3. 窄授权（scoped）覆盖它命名的那一族，含被标记的调用
4. 预授权作用域（CI 清单）对无人值守同理
5. 宽授权（tool 级）只覆盖未被标记的调用
6. 无人可问时，ASK 变成 DENY
```

第 3 与第 5 的不对称是支点：**授权的强度应当与它的宽度成反比。**

- `bash` = 宽而弱 → 不覆盖被标记的调用
- `bash:git push` = 窄而强 → 覆盖该族，含被标记的

**为什么第 2 步在第 1 步之后**：BYPASS 必须真的短路一切，包括只读检查。
如果只读检查在前，BYPASS 就不是 BYPASS，而是一个非常宽松的授权——这两件事
在审计上的含义完全不同（`rule="bypass"` vs `rule="read_only"`）。

**代价**：`decide()` 有九个 return，`PLR0911` 会报。我在 `pyproject.toml` 里
为这个文件单独关掉了它，理由写在配置旁边——把九个分支折成表或折成一串辅助
函数，会让**顺序**（最需要被 review 的东西）变得难读。

## 3. 决策是资源，不是函数调用

`POST /v1/decisions` 返回一个 `decision_id`，回答走
`POST /v1/decisions/{id}/answer`。

**为什么不做成无状态的 `POST /v1/check`**：弹框是一个往返。agent 问，人去答，
服务必须在中间**记住那个问题**。如果裁决是无状态的，那么「回答」请求到达时
服务不知道人在回答什么——它只知道「有人说了 always」，而「always 什么」
已经丢了。

有了 decision_id，回答是对一行的追加，而且：

- 审计表能回答「谁在什么时候批准了什么」
- 回答**不可覆盖**（重放返回 409）——重写一个人做过的决定是审计表唯一绝不能
  允许的事
- `grant_for_answer()` 能读到 `rule`，从而知道这次调用**是不是被标记过**，
  进而决定「always」该不该记录授权

**代价**：每次请求一次写库（见 §7）。

## 4. 存储：三个不显然的决定

### 4.1 `scope` 用空串，不用 NULL

```sql
UNIQUE (project_id, tool, scope)
```

**SQLite、PostgreSQL、MySQL 都把 UNIQUE 索引里的 NULL 当作互不相同。**
所以如果 `scope` 可空，`(1, 'bash', NULL)` 可以插入任意多次——唯一约束对
**最常见的 tool 级授权**完全失效。

空串表示「无作用域」。`Grant.key` 负责在两种表示之间转换
（`bash` ↔ `tool="bash", scope=""`）。

**代价**：语义上「空」和「没有」是两个概念，用一个值表示它们需要在文档里说清。

### 4.2 幂等写入靠唯一约束 + 冲突后重读

```python
existing = select(...)          # 快路径：已经存在就直接返回
if existing: return existing, False
try:
    session.flush()             # 让数据库的约束来裁决
except IntegrityError:
    session.rollback()
    return re_read(), False     # 竞态中输掉的那个重读赢家的行
```

**为什么不是「先查再插」就够**：两个并发请求可以同时查到「不存在」，然后
同时插入。唯一约束选出赢家，输的那个重读。少了这一步，一个新工作区的第一个
请求就是一个竞态。

**代价**：一次 `flush` 失败要 rollback 整个事务。这里没问题（事务里只有这一
次写），但如果将来同一个事务里还有别的写，顺序就要小心。

### 4.3 决策的审计行和它创建的授权在同一事务

**一条存在、但没有记录的授权**，是审计表唯一不能出现的状态。

**代价**：授权写入的失败会连带回滚审计行，所以「回答成功」和「审计已落库」
必须是同一件事——这是对的，但意味着回答接口不能对审计失败做降级。

### 4.4 回答的原子性靠条件 UPDATE，不靠行锁

回答一个弹框时，「这个决定有没有被回答过」的检查**不能由读来裁决**：

```python
row = session.get(Decision, decision_id)
if row.answer is not None:          # ← 两个并发请求都会读到这里是 None
    raise AlreadyAnswered(...)
row.answer = answer                 # ← 后写的那个静默覆盖前一个
```

两个请求同时到达，都读到「未回答」，都通过检查，第二个人的答案覆盖第一个人的。
审计表里留下一条**看起来正常、实际被改写过的**记录——这正是它最不能有的状态。

**修法不是行锁。** 直觉方案是 `SELECT ... FOR UPDATE`，但 SQLAlchemy 把这条
子句编译到 SQLite 时**直接丢掉**，渲染出的 SQL 里没有 `FOR UPDATE`（实测，
见 `tests/integration/test_concurrent_answers.py` 的模块文档）。也就是说行锁会
在 CI 的 PostgreSQL 上生效，而在**默认部署**的 SQLite 上不存在——一个只在测试
环境成立的保证，比没有保证更危险，因为它会让人以为已经安全了。

真正跨后端成立的是条件 UPDATE，由数据库在一次语句里完成比较与交换：

```python
UPDATE decisions SET answer = :answer, ...
WHERE id = :id AND answer IS NULL      # ← 胜负在这里决出
```

`rowcount` 就是判据：1 表示这次调用是写下答案的那一次，0 表示行不存在或已被
别人抢先。调用方据此区分 **404**（不存在）与 **409**（竞态失败）。

**代价**：这条 UPDATE 绕过了 ORM 的身份映射（`synchronize_session=False`），
所以同一事务里如果还持有该行的对象副本，它是过期的。这里没有——读到的 `row`
只用来取 `project_id`、`tool`、`rule` 等不变字段，写完全交给这条语句。

**失败方不留痕迹**：`always` 会创建一条授权，而授权写入在条件 UPDATE **之前**。
所以失败方抛异常时，外层 `except` 回滚整个事务，那条授权一起消失。否则会出现
「回答被拒了，但授权还在」——一个只有并发时才出现的提权。

### 4.5 append-only 由数据库强制，不由约定

上面三节都在说「服务怎么写」。这一节说的是**除了服务，谁还能写**。

`decisions` 一直被称为 append-only，这在代码层面是真的：`DecisionRepository`
除了那一次回答转变之外不发 UPDATE，UPDATE 之外一条 DELETE 都没有。但它**不是
数据库层面的真**——一条迁移、一个拿着 `psql` 的人、一段将来写的 bug，都能改写
某条已记录的决策，留下的行**看起来完全正常**。审计表最不能有的失败正是这种：
不是数据错了，而是错误没有形状。

所以规则下沉成触发器，两个后端各一套，**行为必须一致**：

| 操作 | 结果 |
|---|---|
| `DELETE` 一行审计 | 拒绝 |
| `DELETE` 它所属的 `projects` 行（级联） | **拒绝**——审计表压过工作区 |
| 第一条回答（null → 值） | 允许 |
| 改写已回答行的 `answer` / `verdict` / `arguments` | 拒绝 |

**级联那条是设计的关键。** `decisions.project_id` 是 `ON DELETE CASCADE`，没有
触发器时，「清空审计表」的办法就是删掉它所属的工作区——历史随之消失，且没有
任何记录表明它曾经存在。现在反过来：**历史获胜，删除失败**。一个能被父行删空的
审计表不是审计表。

**为什么是两张后端各一套 DDL 而不是一个通用写法**：SQLite 用
`CREATE TRIGGER ... WHEN NOT (...)` 逐列比较 `OLD`/`NEW`，PostgreSQL 用 plpgsql
函数 + `IS DISTINCT FROM`。两者能表达的规则**恰好一样**——这是实测的，不是推断的
（`tests/integration/test_append_only_audit.py` 在两个后端上跑同一批裸 SQL 断言）。
`storage/triggers.py` 对未知方言**抛异常而不是静默跳过**：一个没装触发器的数据库
看起来受保护、实际不受保护，这比不宣称这条保证更糟。

**代价**：DELETE 现在会失败，所以「删掉一个工作区来清理它的数据」不再可行——
这是有意的，但它意味着数据生命周期（保留期、GDPR 式删除）需要一个新的机制：
显式的归档表或带审计的清理流程，而不是级联删除。这一版没有做，因为**正确做法
是产品决策**（保留多久、谁有权删、删除本身要不要留痕），而不是顺手加一句 DELETE。

## 5. 授权缓存：这个服务唯一可能出错的地方

缓存页面读到旧数据，是显示了昨天的价格。**缓存授权读到旧数据，是服务在用户
已经撤销之后继续放行。**

### 5.1 失效必须在 commit **之后**

```python
session.commit()
...
self._cache.invalidate(project_id)   # ← 在这里，不是前面
```

**先失效会怎样**：会有一个窗口，期间一个并发请求读到**写之前**的授权集合，
把它缓存下来，**并带上一个全新的 TTL**。然后那次写提交了，而缓存永远不会
知道——它会一直服务旧集合直到 TTL 过期。

这个竞态很窄，但后果是「用户撤销了一个授权，服务还在照着它放行」。

### 5.2 每次写都失效，包括没匹配到的

`revoke` 在 `removed == 0` 时**也**失效缓存。理由：调用方以为有东西在那里。
给他缓存的集合，就是告诉他「它还在」。

### 5.3 TTL 是跨进程兜底，不是机制

**多进程下的缺口，明说而不是藏起来**：两个 worker 时，worker A 处理的撤销对
worker B 不可见，直到 B 的条目过期。诚实的选项是共享缓存 + 失效广播，或者
一个短到可以作为产品决策的 TTL。这个项目实现了 TTL 并**命名了这个缺口**；
它不假装 TTL 是同一件事。

### 5.4 缓存可以关掉

`PERMGATE_GRANT_CACHE_ENABLED=false` 是一个**受支持的配置**，不是调试开关。
「正确但更慢」必须在有人排查线上不一致时可用。

### 5.5 淘汰是「最早过期优先」，不是 LRU

访问模式是一个活跃项目一条，工作集很小，LRU 的额外记账比它省下来的更贵。
**把这件事说出来比那几微秒重要**——一个不是 LRU 的「LRU」断言，只在出事故的
时候才会被发现。

## 6. API 与错误契约

### 6.1 错误响应只有一种形状

```json
{"error": {"code": "...", "message": "...", "details": {...}, "request_id": "..."}}
```

解析三种错误格式的客户端一种都不会解析。

- **服务异常自带 `status_code`**：映射写在异常类旁边，而不是三个模块之外的
  一个 handler 分支里
- **未预期异常不泄漏文本**：响应体里的堆栈是信息泄漏。真正有用的是
  `request_id`——它把用户的报告和日志里的完整堆栈对上

### 6.2 运行模式默认不能由客户端指定

能选模式的客户端能选 `BYPASS`，那会让整个服务变成装饰。

`BYPASS` 即使在允许自选模式时也默认不服务，而且是**在 API 边缘拒绝**，
不是在引擎深处——这样它不可能因为「某处忘了加检查」而被走到。

### 6.3 `/v1/rules` 存在

一条没人能查看的规则层，是一条没人能质疑的规则层。「现在到底什么在白名单上」
应该是一个 curl 的答案，而不是一个关于部署了哪个版本的问题。

## 7. 可观测性，和为什么审计写入没被优化

### 7.1 指标标签是封闭枚举

`rule` 来自 `domain.decision.Rule` 枚举，所以标签基数被代码里的规则数量限死。
如果把原始的 `reason` 字符串当标签，基数会随语料增长——每多一种命令形状就多
一条时间序列。**这是打垮指标后端的经典方式。** 理由属于日志和审计表；计数
属于 Prometheus。

### 7.2 延迟直方图自定义分桶

Prometheus 默认桶从 5ms 起。一次决策是几次字符串比较加一次索引读，绝大多数
流量会落进第一个桶——那个直方图什么都没测。所以桶从 50µs 起。

### 7.3 liveness 不碰数据库

`/healthz` 只回答「这个进程还活着」。`/readyz` 才碰数据库，因为那才是它的问题。

一个数据库慢就失败的 liveness 探针，会让容器被杀掉重启——**既不修数据库，
又丢掉在途的审计行**。

### 7.4 为什么审计写入故意没优化

压测显示审计写入是一次请求的主要成本（关掉它 p50 减半、p99 降 43%）。
三条路都看过：

| 方案 | 收益 | 代价 |
|---|---|---|
| 缓冲/批量提交 | p50 再降一半以上 | **崩溃时丢一批审计行**——审计表丢了行，等于回答「上周二 agent 跑了什么」时给出一个不完整的答案，而**不完整的审计答案比没有答案更危险，因为它看起来是完整的** |
| 异步写入 | 请求不等落库 | 「接口返回成功」和「审计已落库」不再是同一件事，调用方无法区分。要区分就得加确认机制，延迟又还回去了 |
| 换 PostgreSQL | 解决并发写入排队 | 不改变「每次请求一次写」的成本结构，只是把排队换个地方；且把部署从「一个文件」变成「一套服务」 |

**要做到批量提交，得先回答「崩溃时丢一批审计行的可接受上界是多少」。**
那是个产品决策，不是技术决策。

**这一版的选择是：测量它、命名它、说清代价，而不是悄悄做掉。**

## 8. 移植与保真度

`domain/` 的规则来自上一轮项目，那个实现有四轮实测加固。移植的可信度靠对拍：

1. `tools/generate_conformance_fixture.py` 跑一次原实现，把 **119 条命令 × 4
   项输出**（黑名单原因 / 白名单原因 / 执行层闸门 / 命令作用域）冻进
   `tests/fixtures/conformance.tsv`
2. `tests/unit/test_conformance.py` 每次运行逐条比对，**包括「没有匹配」这件事**

477 条断言。

### 8.1 对拍时发现的原始错误

原报告里「改造前的无人值守」那一行用的是**改造后**的执行层闸门，而不是当时
真实存在的旧闸门。后果：把 16/24 报成了 24/24，等于替旧代码记了一次它没做过的
放行。

敞口那一列（8/25）不受影响，因为两种闸门对危险命令判断一致。

### 8.2 结构性修复

原实现把执行层闸门写成一个全局函数，所以「改造前」的基线会被「改造后」的
闸门审判——**实验替旧代码修好了它当时并没有修的 bug**。

新实现把闸门绑定在**策略对象**上：

```python
class LegacyPolicy:
    def gate(...): return check_dangerous(...)      # 当时的闸门
class AllowlistPolicy:
    def gate(...): return execution_block(...)      # 现在的闸门
```

换策略必须同时换闸门，所以这个错误在结构上不可能再犯。
`tests/unit/test_regression_metrics.py` 把 16/24 钉成了断言。

## 9. 明示的边界

| 缺口 | 说明 |
|---|---|
| **没有沙箱** | 白名单不隔离进程。`make` / `pytest` 执行项目自身的代码并被背书，因为跑不了测试的 agent 没人用。管住的是 agent 会做什么，不是代码会做什么 |
| **威胁模型是「agent 跑偏」** | 不是「仓库本身恶意」。后者要 seccomp / sandbox-exec 那个量级 |
| **多进程撤销有可见性延迟** | 上界 = TTL（默认 15s） |
| **不做语义判断** | 读的是词法。变量展开后才变成 `rm -rf /*` 的命令，规则层在展开前无从判断 |
| **脱敏只认「凭据形态」** | 凭据形态的参数不写进审计行（只留摘要，见 `storage/redaction.py`）。但 `--password=hunter2`、裸的 base64、以及「命令没点名、内容却是私钥的文件」都不认——把它扩成通用密钥检测是另一个量级的工作，误报率会先垮掉。要更严就整体关掉 `audit_store_arguments`，那样每次调用都只留摘要 |
| **PostgreSQL 的写者排队已测量，但它不解决尾延迟** | 两种后端在同一个进程、同一批语料、1/2/4/8/16 线程下都量过（`loadtest/backends.py`，数字见 §1.3）。结论不是「PG 更快」：SQLite 的中位数几乎不随并发上升（1.8×）而 p99 涨 35×，PG 反过来（中位数涨 12×、尾部在 8 线程前明显更好）。**到 16 线程两者收敛到同样差的尾部（1.07×）**。三个解释被测过两个被否掉：不是 fsync（`synchronous_commit=off` 省 1.00×，服务器确为 `fsync=on`）、不是连接池（池 20 与默认 5 中位数相同）。**「测过正确性」和「压测过」仍是两件事**——这次只补上了后者的一半：单机、单一数据集、无真实客户端分布 |
