# permgate —— Agent 工具调用权限网关

一个独立部署的后端服务：agent 每次执行工具调用前向它请求裁决，它返回
`allow / ask / deny` + 理由 + 授权作用域，并把每一次决策落进审计表。

**它不是**模型推理引擎、不是 agent 框架、也不是已经上线的生产系统。

---

## 1. 它解决什么问题

AI agent 会执行 shell 命令。市场上所有 agent 产品的权限层都栽在同一个地方：

> **「这条命令看起来危不危险」是一个无法穷举的问题。**
> `terraform destroy -auto-approve` 和 `kubectl delete namespace production`
> 是灾难性的，而任何"看起来危险"的正则都抓不到它们——危险在程序**做什么**，
> 不在它**怎么写**。

这个项目把问题反过来问：**这条命令我们能不能为它背书？** 不能背书的，全部
送到人面前。同时它回答第二个问题：一次「总是允许」到底授权了多大范围。

```
被测语料：24 条合法命令（其中 16 条完全安全、8 条会不可逆地丢东西）+ 25 条危险命令

  策略                     召回率    打扰率    误伤率
  黑名单：列出危险的         68%      33%      50%
  白名单：列出已知安全的    100%      33%       0%
```

打扰率两者相同，误伤率从 50% 降到 0%。**这两个指标必须分开报**——把它们
混成一个数字，会让人以为只要调调规则就能把那 33% 降下去，而降不掉（见 §5）。

### 1.1 它从一个真实缺陷开始

授权是**按工具**记录的。用户在 `bash` 上一次「总是允许」之后，该工具后续
所有调用永久免问。实测在这个模型下：

```
信任型用户按一次 always 之后        弹框 1 次
  其中 8 条危险命令在零感知下执行   ← 敞口
  24 条合法命令被静默拦掉          ← 用户对 agent 的行为有错误认知
```

四轮改造的结果（同一批语料、同口径、可复现）：

| 配置 | 弹框 | 静默拦截 | **零感知危险执行** |
|---|---:|---:|---:|
| 改造前 · 信任型 | 1 | 24 | **8** |
| 第一轮（黑名单接入同意层） | 26 | 0 | **8** |
| 第二轮（授权按项目隔离 + 可撤销） | 26 | 0 | **8** |
| 第三轮（翻转成安全命令白名单） | 34 | 0 | **0** |
| 第三轮 · 谨慎型 | 49 | 0 | **0** |

**只有第三轮是安全收益。** 第一轮买到的不是安全，是**可见性**；第二轮一次
判定都没改，买到的是授权可解释、可撤销——而第三轮那 34 次弹框之所以能落地，
前提正是第二轮。这三轮的边界是实测出来的，不是设计时想清楚的。

## 2. 快速开始

```bash
uv venv --python 3.10 .venv
uv pip install --python .venv/Scripts/python.exe -e ".[dev]"

# 分类一条命令。不连数据库、不起服务
uv run permgate classify "rm -rf ./build"

# 建一个调用方凭证。服务默认要求身份认证，没有客户端它不会启动，
# 所以这是起服务之前的一步。token 只打印这一次，库里只存它的摘要。
uv run permgate client create --name me --root /home/dev/checkout-api

# 起服务
uv run permgate serve
# 打开 http://127.0.0.1:8000/docs
```

```bash
# 问一次裁决。所有业务端点都要带 bearer token
curl -s localhost:8000/v1/decisions \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer <上面的 token>' -d '{
  "project_root": "/home/dev/checkout-api",
  "tool": "bash",
  "arguments": {"command": "terraform destroy -auto-approve"}
}'
```
```json
{
  "decision_id": "8f14e45f-ceea-467a-9a5d-1c1b0b7c1a2e",
  "verdict": "ask",
  "rule": "risk_flagged",
  "reason": "`terraform` is never auto-approved",
  "scope": "terraform destroy -auto-approve",
  "latency_us": 1910,
  "project_root": "/home/dev/checkout-api"
}
```

> `latency_us` 是**热请求**的实测值（§6 里服务的 p50 是 813µs）。
> 对空库的第一次请求要十几毫秒，因为它顺带建了表——那不是判定的成本。

```bash
# 人回答了：把授权收敛到这一条命令模式上，而不是整个 terraform
curl -s localhost:8000/v1/decisions/8f14e45f.../answer \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer <token>' -d '{"answer": "scoped"}'
```
```json
{
  "decision_id": "8f14e45f-ceea-467a-9a5d-1c1b0b7c1a2e",
  "answer": "scoped",
  "granted_key": "bash:terraform destroy -auto-approve",
  "grant_created": true
}
```

```bash
# 撤销它。key 里有空格，URL 路径段必须百分号编码。
# removed=1 是撤掉了一条，0 是本来就没有
curl -s -X DELETE -H 'authorization: Bearer <token>' \
  "localhost:8000/v1/grants/bash%3Aterraform%20destroy%20-auto-approve?project_root=/home/dev/checkout-api"
```
```json
{"project_root": "/home/dev/checkout-api", "key": "bash:terraform destroy -auto-approve", "removed": 1}
```

> **两个容易踩的地方。**
>
> **`scope` 里带着标志**（`-auto-approve`），不是只有 `terraform destroy`。
> 这不是啰嗦——`-auto-approve` 恰恰是让这条命令无需人在场就能跑的那个标志，
> 把它排除在授权之外，等于授权了一条比用户以为的更窄、但更安全的命令。
>
> **撤销接口把 key 放在 URL 路径里，而 key 通常含空格**，所以必须百分号编码。
> Python、JS、Go 的 HTTP 客户端都自动做这件事，裸 `curl` 不会。

```bash
# 跑评测（离线，零成本）
uv run permgate eval
# 跑分层延迟压测
uv run python loadtest/benchmark.py
```

## 3. 架构

四层，依赖单向向下。**领域层是纯的**——没有 IO、没有配置、没有日志，
`decide()` 是它参数的函数，别的什么都不是。

```
api/          HTTP、DTO、错误映射        ─┐
services/     事务边界、缓存失效、审计    │  可以有 IO
storage/      SQLAlchemy、仓储、缓存      │
domain/       规则表、分类器、决策引擎   ─┘  纯函数，零 IO
```

这个约束不是洁癖，它买到三件事：

1. **规则层能离线评测。** `eval/` 用 49 条标注命令 + 11 条真实事故命令跑完整
   分类器和四种历史配置，不需要服务器、数据库、网络。§1 和 §5 的数字全部
   来自这里，可复现。
2. **规则层能被穷举测试。** 713 个测试，10 秒跑完，覆盖率 94%。
3. **性能瓶颈的位置是显然的。** 因为 `decide()` 是纯的，它唯一可能慢的原因
   是它的输入拼装得慢——这把整个性能预算压到授权查询和审计写入上。§6 的
   测量证实了这一点，而且结论和直觉相反。

### 3.1 决策顺序就是安全模型

```
1. BYPASS 短路一切（--dangerously-skip-permissions，且部署必须显式打开）
2. 只读工具永不打扰人
3. 窄授权（scoped）覆盖它命名的那一族，被标记的调用也覆盖
4. 预授权作用域（CI 清单）对无人值守同理
5. 宽授权（tool 级）只覆盖未被标记的调用
6. 无人可问时，ASK 变成 DENY
```

第 3 步和第 5 步的不对称是整个设计的支点：

> **授权的强度应当与它的宽度成反比。**
> 宽而强 = 那个漏洞（一次 always 授权整个 bash）；窄而弱 = 毫无用处
> （用户想不再被问的，恰恰是被标记的那些调用）。

所以：`bash` 是**宽而弱**的（不覆盖被标记的调用），`bash:git push` 是
**窄而强**的（覆盖该族，包括被标记的）。实测：授权粒度停在程序级（`git`）
会让 `git push --force` 一起进来，敞口 0 → 1；下沉到命令模式（程序 + 动词 +
标志）后敞口回到 0，同时 CI 合法命令 24/24 全放行。

### 3.2 审计

每一次请求写一行，**包括被放行的**。只记拒绝的审计表回答不了「上周二 agent
到底跑了什么」，而那才是人们真正会问的问题。写入与它可能创建的授权在同一个
事务里——一次崩溃不能留下一条没有记录的授权。

## 4. API

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/v1/decisions` | 裁决一次工具调用 |
| `POST` | `/v1/decisions/{id}/answer` | 记录人给出的回答 |
| `GET` | `/v1/grants` | 当前有哪些standing 授权 |
| `POST` | `/v1/grants` | 运维直接预授权（不经弹框） |
| `DELETE` | `/v1/grants/{key}` | 撤销一条 |
| `DELETE` | `/v1/grants` | 清空一个项目的全部授权 |
| `GET` | `/v1/audit` | 决策与执行的审计流 |
| `GET` | `/v1/rules` | **当前运行的规则表本身** |
| `GET` | `/healthz` `/readyz` `/metrics` | 运维 |

**为什么裁决是一个带 id 的资源，而不是一个无状态函数调用**：弹框是一个往返。
agent 问，人去答，服务必须在中间记住这个问题。于是决策是一行记录，回答是对
那一行的追加——而且**不能覆盖**（重放返回 409），重写一个人做过的决定是审计
表唯一绝不能允许的事。

`/v1/rules` 存在的理由：一条没人能查看的规则层，是一条没人能质疑的规则层。
「现在到底什么在白名单上」应该是一个 curl 的答案，而不是一个关于部署了哪个
版本的问题。

## 5. 实测数据

### 5.1 判别质量与代价

```
语料：24 条合法命令（16 条完全安全 / 8 条会不可逆丢东西），25 条危险命令

  黑名单（改造前）   召回 68%   打扰 33%   误伤 50%
  白名单（现在）     召回 100%  打扰 33%   误伤  0%
```

- **打扰率**：合法命令被问的比例——用户在承受的摩擦
- **误伤率**：完全安全却被问的比例——工具判错了，**只有这部分可以优化**

两者都是 33% / 0% 这件事很重要：剩下的 33% 全部问在**真正有后果**的命令上
（`git clean -fd` 删未跟踪文件、`docker compose down -v` 删卷、`pip install`
执行网络脚本）。**这部分是刚性成本。**

> 这个项目一度把 42% 叫作「误伤率」并计划去优化它。拆开指标后发现 42% 是
> 打扰率，真实误伤率是 0%——那个方向结案为「无事可做」。**知道哪一半降不掉
> 是结论；知道整块都降不掉也是结论，而且更值钱，因为它拦住了下一轮的无用功。**

### 5.2 样本外检验

自造语料的问题是：白名单是照着它设计的，用它测白名单等于用训练集测模型。
所以另收 11 条**公开事故报告里真实执行过的命令**（每条带出处，判别器设计时
从未见过）：

| | 样本内（自造 49 条） | 样本外（真实事故 11 条） |
|---|---:|---:|
| 旧黑名单 | 68% | **36%** |
| 新白名单 | 100% | **100%** |

**自造语料把旧机制的能力高估了近一倍。** 而白名单在样本外补测时曾漏掉一条
`rm -rf src/modules src/drivers src/kernel`——它背书了它，因为代码注释里写的
理由是「相对路径出不了项目树，而且 git 能恢复的东西都是可恢复的」。**后半句
是假的**：那些文件从未进过 git（claude-code#23913 删了 2229 个未跟踪源文件，
只有 16 个曾进入过任何一次提交）。理由换成真的之后（递归删除只对构建产物放行，
因为构建产物按定义可以重建），样本外 11/11，而打扰率和误伤率一个都没变。

### 5.3 无人值守

一个标志能把前三轮全部绕过：

| 模式 | 危险命令放行 | 合法命令放行 |
|---|---:|---:|
| 改造前的 `--yes`（无条件） | **8**/25 | 16/24 |
| 现在的 `--yes`（放行例行、拒绝被标记的） | 0/25 | 16/24 |
| 现在的 `--yes` + CI 预授权清单 | 0/25 | **24/24** |

CI 清单是按**命令模式**（程序 + 动词 + 标志）列的，共 8 条。它由**合法**命令
生成、拿**危险**命令和 11 条样本外真实事故命令去撞——零命中。这说明这一层的
颗粒度够了：它能把「流水线要跑的」和「绝不能无人值守跑的」分开。

## 6. 性能

分层测量，因为「快不快」不是问题，「时间花在哪」才是。

| 层 | p50 | p99 | ops/s |
|---|---:|---:|---:|
| 纯引擎（零 IO） | 27µs | 74µs | 28,958 |
| 服务 · 无缓存 | 995µs | 3,926µs | 848 |
| 服务 · 有缓存 | 813µs | 3,175µs | 1,019 |
| 服务 · 关审计 | **499µs** | **993µs** | 1,869 |
| 服务 · 8 线程 | 884µs | **110,545µs** | 942 |
| HTTP · 4 线程 | 4,914µs | 97,447µs | 366 |

三个结论，**两个和直觉相反**：

1. **规则层只占一次请求的 3%。** 优化匹配器等于什么都没做。架构让这件事
   可查而不是可争：`decide()` 是纯的，所以它能被单独计时，不用起服务器。
2. **瓶颈是审计写入，不是授权查询。** 关掉审计 p50 减半、p99 降到三分之一；
   而授权缓存只省 18%。直觉会猜数据库**读**是成本，实测反了。
3. **并发吃掉的是尾延迟，不是中位数。** 8 线程下 p50 几乎不动，p99 从
   3.2ms 涨到 110ms——SQLite 串行化写入，它们排队。中位请求没问题，排在
   七个写者后面的那个有问题。

**下一步的靶子因此是审计写入的批量/缓冲提交——而这一版故意没做**，理由见
`docs/architecture.md`：让那次写入变便宜的每一种办法，都在拿审计表存在的意义
去换。测量它、命名它、说清代价，比悄悄做掉更有价值。

机器事实随数字一起打印（Windows 10 / 16 核 / CPython 3.10.6）。没有机器信息的
延迟数字不是测量。

## 7. 工程决策

面试会问的那些，每条都有理由和代价。

| 决策 | 为什么 | 代价 |
|---|---|---|
| **领域层是纯的** | 规则层能离线评测、能穷举测试、瓶颈位置显然 | 服务层要负责把 inputs 拼装好 |
| **决策是资源不是函数调用** | 弹框是往返，必须记住「问题」 | 每次请求一次写库 |
| **`scope` 用空串不用 NULL** | SQLite/PostgreSQL/MySQL 都把 UNIQUE 里的 NULL 当互不相同，可空 scope 会让最常见的 tool 级授权重复插入 | 语义上「空」表示「无作用域」，要在文档里说清 |
| **缓存失效在 commit 之后** | 先失效会留一个窗口，并发请求把**写之前**的授权集合缓存下来并带上新 TTL | 代码上有顺序依赖，注释必须解释 |
| **回答不可覆盖（409）** | 重写一个人做过的决定是审计表唯一绝不能允许的事 | 客户端要处理冲突 |
| **运行模式默认不能由客户端指定** | 能选模式的客户端能选 BYPASS，那会让整个服务变成装饰 | 多一个部署开关 |
| **策略对象承载冻结的历史配置** | 「改造前敞口是 8」必须能被**重新测量**，而不是被记住 | 多一层间接 |

最后一条来自一个真实的踩坑：前一版把执行层闸门写成全局函数，于是「改造前」
的基线被**改造后**的闸门审判，实验替旧代码修好了它当时并没有修的 bug——基线
污染。现在闸门绑定在策略对象上，这个错误在结构上不可能再犯。

## 8. 状态：已实现并验证 / 计划实现 / 明确不做

**已实现并有测试覆盖（713 个测试 / 覆盖率 94% / `ruff` 与 `mypy --strict` 全绿）**

- 命令词法、白名单分类、命令模式抽取（**119 条命令 × 4 项输出与原实现逐字对拍**）
- 决策引擎的全部六个分支，含授权宽度/强度不对称
- SQLite 持久化：唯一约束、幂等写入、事务边界、级联删除
- 授权缓存：TTL、容量上限、**每次写入后失效**（撤销立即生效）
- HTTP 服务：两阶段决策流、授权管理、审计查询、错误契约、请求 ID
- 可观测性：Prometheus 指标、结构化日志、liveness/readiness
- 命令行：`classify`（离线，不连库）/ `decide` / `grants` / `revoke` / `audit` / `eval` / `serve`
- 离线评测门禁：把已发布的数字钉在测试里（`tests/unit/test_regression_metrics.py`）
- Alembic 迁移，含**迁移与模型一致性**检查（`compare_metadata` 必须零差异）

### 8.1 质量门禁

每一个门禁都是这个项目**已经失败过一次**的那一类：

```bash
ruff check src tests eval tools migrations   # 曾漏掉一个缺 import —— 278 个测试没抓到那次崩溃
ruff format --check src tests eval tools
mypy                                          # strict；配置写了一段时间没人跑，跑出 13 个错
pytest tests/ --cov=permgate --cov-fail-under=90
```

`.github/workflows/ci.yml` 跑六个 job：`lint` / `types` / `test`（3.10–3.12 矩阵）/
`migrations`（含从空库迁移与 downgrade 往返）/ `evaluation`（重测已发布的安全数字）/
`docker`（构建镜像、起容器、打一次真实决策）。

**门禁写在配置文件里不算数，跑起来才算。** 上面注释里的两次事故都不是假设——
所以这一节列的是命令，不是决心。

**计划实现**

- 审计写入的批量提交（§6 指出的靶子）——需要先把「崩溃时丢一批审计行」
  这件事的取舍写清楚
- Redis 共享缓存 + 失效广播，解决多进程下撤销的可见性延迟
- Alembic 迁移已搭好，但只有一条初始版本

**明确的边界（不假装做了）**

- **没有沙箱。** 白名单不隔离进程。`make` 和 `pytest` 会执行项目自身的代码
  （`pytest` 会加载 `conftest.py`），它们被背书，因为一个跑不了测试的 agent
  没人会用。**它管住的是 agent 会做什么，不是代码会做什么。**
- **威胁模型是「agent 跑偏」，不是「仓库本身恶意」。** 后者要 seccomp /
  sandbox-exec 那个量级的东西，规则层解决不了。
- **多进程下撤销有可见性延迟**，上界是 TTL（默认 15s）。
- **不是语义判断。** 它读的是词法。`claude-code#82165` 那类"变量展开后才变成
  `rm -rf /*`"的命令，规则层在展开前无从判断——那是它标注的边界，不是它的 bug。

## 10. 来源与血统

规则表、分类语义、`decide()` 的判定顺序，移植自本人针对开源教学项目
**CoreCoder** 所做的一次权限模型改造（四轮，带完整的实验与样本外检验）。
服务层、存储、缓存、API、可观测性与性能工程是这个项目新增的。

移植不是重写：`tests/fixtures/conformance.tsv` 冻结了原实现对 119 条命令的
四项输出，`tests/unit/test_conformance.py` 每次运行都逐条比对。**这是一次
被验证过的移植，不是一句「我移植了」。**

移植过程中发现了原报告的一处测量口径错误：实验 B2 里「改造前的 `--yes`」那一行
用的是**新**闸门而不是当时真实存在的旧闸门，于是把 16/24 报成了 24/24，等于
替旧代码记了一次它没做过的放行。敞口那一列（8/25）不受影响，因为两种闸门对
危险命令判断一致。这个错误在新项目里由「闸门绑定策略对象」在结构上排除。

## 11. 血统、协作方式

### 11.1 哪些是移植的，哪些是这个项目新增的

这个区分比它看起来重要：评审时「哪部分是你的判断」和「哪部分是你的实现」是两个
不同的问题，把两者混在一起回答，两个都答不好。

| 部件 | 来源 |
|---|---|
| `domain/rules.py` 规则表、`domain/bash_policy.py` 分类器、`domain/engine.py` 的 `decide()` 顺序、`domain/lexer.py` 词法 | **移植**，来自上游授权层的四轮改造 |
| `eval/corpus.py` 语料与 `eval/real_incidents.py` 事故集 | **移植**，在本项目里扩充并加了回归门禁 |
| `services/`、`storage/`、`api/`、`observability/`、`cli.py` | 本项目新增 |
| `migrations/`、`loadtest/`、`Dockerfile`、`docker-compose.yml`、`.github/workflows/ci.yml` | 本项目新增（上游是库，没有服务端这些东西） |

移植的部分以 `tests/fixtures/conformance.tsv` 为准：119 条命令 × 4 项输出与原实现
逐字对拍，`tests/unit/test_conformance.py` 每次运行都比对。**移植是被验证的，
不是被声称的。**

### 11.2 协作方式

这个项目的实现过程使用了 AI 编码助手。把它写在这里，不是因为需要道歉，而是因为
一篇主张「测量而不是记忆」的文档，不该对读者隐瞒自己是怎么被造出来的。

分工大致是：**设计判断、取舍与验收标准由人做出，实现与文档撰写在 AI 助手的参与下
完成。** 区别是实质性的，而且是可以被检验的——下面这些决定是项目的支点，也是评审
时最该被追问的地方，它们不来自「生成一份代码」，而来自对问题的判断：

- 领域层约束成纯函数，并因此换来离线评测、穷举测试和**瓶颈位置可单独计时**；
- 授权强度与宽度成反比的规则，以及第 3、5 步的不对称；
- 缓存失效放在 `commit` 之后，而不是之前；
- 决策落库为带 id 的资源（因为弹框是一个往返）；
- 打扰率与误伤率**分开报**，即便合并成一个数字更好看。

### 11.3 本仓库的已知脆弱点

文档与代码存在手工耦合：README 与 `docs/` 里多处行数、测试数、模块清单需要人工同步，
改动代码后忘记同步就会产生一处无人发现的谎言。这是已知的、尚未修掉的问题——它出现
在「诚实报数」是核心主张的项目里，因此列出来而不是等评审发现。
